## Architecture (as mapped during the audit)

sqlpipe is a header+single-TU C++23 SQLite streaming-replication library shipped as dist/sqlpipe.h (public API) and dist/sqlpipe.cpp (~5,700 lines of sqlpipe logic, followed by bundled sqlift ~lines 5709-8495 and sqldeep/liteparser ~8496-end). It is "message-in/message-out": the caller supplies the transport, sqlpipe serializes/deserializes wire bytes and mutates a caller-owned sqlite3* via the session/changeset extension. Four roles sit over one Impl-per-object pimpl each: Master (sending side; owns a sqlite3session on "main", assigns monotonic Seq, keeps a changeset replay deque), Replica (receiving side; applies changesets, drives diff-sync state machine, hosts a QueryWatch for subscriptions and a SAVEPOINT-based "prediction" mechanism), Peer (wraps a Master+Replica behind a symmetric API with a SenderRole-tagged PeerMessage and glob-based ownership negotiation), and Relay (Master+Replica on the SAME handle, fanning changesets to sinks). Database is a convenience wrapper adding sqlift auto-migration and sqldeep transpilation.

Data flow for live streaming: Master::exec/flush → sqlite3session_changeset → LZ4-framed ChangesetMsg → Replica::handle_message → sqlite3changeset_apply with a conflict callback → AckMsg. Data flow for diff sync (reconnect): HelloMsg (schema fingerprint + last_seq) → BucketHashesMsg (per-table XOR-of-row-hashes buckets keyed by rowid range) → master compares buckets → NeedBucketsMsg (mismatched ranges) → RowHashesMsg (RLE per-row 64-bit FNV-1a hashes) → master diffs → DiffReadyMsg (INSERT patchset + per-table delete rowid lists) → replica applies inside a transaction with foreign_keys temporarily OFF → AckMsg → Live. Fast-reconnect and changeset-queue-replay shortcuts skip the diff when seqs align.

Threading/concurrency model: strictly single-threaded per object, with NO synchronization primitives anywhere (no mutexes, atomics, or documented thread-safety contract). All shared mutable state lives in each Impl and is touched without locking. The one implicit reentrancy path is Master's SQLite commit_hook (commit_hook_cb sets flush_pending, guarded by in_auto_flush to avoid recursion during auto_flush). The header comments say objects don't own the sqlite3*, but they never state the single-thread requirement, so it is an assumed-not-enforced invariant.

The wire format ([4B LE length][1B tag][payload], changeset sub-framing [u32 len][u8 type][data]) is implemented THREE times that must stay bit-compatible: canonical C++ serialize/deserialize (dist/sqlpipe.cpp), a separate ad-hoc result-encoding in the C-API shims (go/sqlpipe/sqlpipe_capi.cpp and web/sqlpipe_wapi.cpp encode_value/encode_handle_result), and a full independent Go reimplementation (go/sqlpipe/serialize.go + deserialize.go + compress.go). Swift consumes the C API via CSqlpipe; Wasm exposes emscripten KEEPALIVE functions to a TypeScript wrapper (web/src).

## Load-bearing invariants

- Master and Replica MUST agree on bucket_size: master computes the compared bucket's hi bound as key.lo + config.bucket_size - 1 (dist/sqlpipe.cpp:1699) and keys buckets by (table, lo). Mismatched bucket_size across sides misaligns bucket boundaries, causing systematic hash mismatch or, worse, missed differences.
- A bucket hash match MUST imply identical bucket contents. Bucket hash is XOR of fnv1a(rowid||row_hash) (dist/sqlpipe.cpp:1100-1103) and the master compares ONLY the 64-bit hash (1690-1695), ignoring the transmitted row_count. Any XOR collision (including compensating pairs of changes) yields a false 'match' and silent, permanent divergence.
- The 32-bit schema fingerprint MUST distinguish incompatible schemas. compute_schema_fingerprint folds sqlift's structural hash through 32-bit FNV-1a (dist/sqlpipe.cpp:709-716); a 2^-32 collision lets a replica with a genuinely different schema pass the Hello check and then apply changesets against the wrong table shape.
- Live-stream changesets MUST arrive in exact seq order: apply_changeset throws ProtocolError unless new_seq == seq+1 (dist/sqlpipe.cpp:4606). Any gap/reorder aborts via a thrown exception rather than graceful recovery.
- Fast-reconnect assumes seq equality implies data equality (dist/sqlpipe.cpp:1521, 4671): if a replica's DB was modified locally while its stored seq still equals the master's, diff sync is skipped and divergence is never detected.
- handle_diff_ready must run as an atomic transaction with FK state restored: it does BEGIN, disables foreign_keys, applies patchset+deletes, COMMIT, re-enables FK (dist/sqlpipe.cpp:4770-4848). An exception thrown in the delete loop leaves the transaction open and foreign_keys OFF (no RAII/rollback on that path).
- RowHashRun.count and the decompressed changeset original_len are attacker-influenced sizes that bound heap allocations; they must be validated before use (they currently are not — see hotspots).
- Peer ownership sets must remain disjoint: their_tables = client's owned_tables, my_tables = complement (dist/sqlpipe.cpp:5354-5355). Overlap would make both sides master the same rows.
- Every tracked table must have an explicit PRIMARY KEY and must not be WITHOUT ROWID (get_tracked_tables, dist/sqlpipe.cpp:749-770); rowid-based diffing and the session extension depend on it.
- Objects are single-threaded; concurrent use of one Master/Replica/Peer/Relay from multiple threads corrupts unsynchronized Impl state (no locks anywhere).

## Trust boundaries

- sqlpipe::deserialize / deserialize_peer (dist/sqlpipe.cpp:508, 5190) — decode caller-supplied transport bytes into Message/PeerMessage. Primary attack surface; a libFuzzer harness exists (tests/fuzz_deserialize.cpp) but only catches sqlpipe::Error, not std::bad_alloc/length_error.
- Reader::read_changeset LZ4 path (dist/sqlpipe.cpp:355-387) and Go readChangeset (go/sqlpipe/compress.go:37-80) — trust a wire-supplied u32 decompressed length to size the output buffer before LZ4 decompress.
- Replica::handle_message / handle_diff_ready — the DiffReadyMsg patchset and per-table delete rowid lists come from a remote master and are applied to the local DB (dist/sqlpipe.cpp:4757-4854); table names are interpolated into SQL (though they originate from the trusted local schema via the diff, not directly from the wire).
- sqlite3changeset_apply on remote ChangesetMsg/patchset bytes (dist/sqlpipe.cpp:4612, 4787) — SQLite parses the raw changeset blob; malformed blobs are SQLite's parsing surface.
- C-API FFI entry points (go/sqlpipe/sqlpipe_capi.cpp, web/sqlpipe_wapi.cpp) — (uint8_t* data, size_t len) pairs from Go/JS, config structs with C-string arrays and function pointers, and callbacks that hand heap buffers (malloc/strdup) back to managed runtimes.
- decode_messages in the C API (sqlpipe_capi.cpp:167-184) — parses a packed [u32 count][msg...] buffer supplied by the managed caller.
- Go/Swift/TS independent wire decoders (deserialize.go, decode.ts) — a second/third parse of the same untrusted bytes that must match the C++ decoder exactly.
- SchemaMismatch auto-migration (auto_migrate_schema, dist/sqlpipe.cpp:790-852) — takes the master's remote_schema_sql string off the wire and feeds it to sqlift parse/diff/apply with SQLIFT_ALLOW_ALL (rebuild+destructive) on the local DB.
- Peer HelloMsg owned_tables (dist/sqlpipe.cpp:5313-5355) — remote-requested table ownership, filtered by table_filter and an optional approve_ownership callback.

### F1 — [CRITICAL] Diff sync identifies rows by rowid, not PRIMARY KEY — wipes/diverges content-identical tables whose PK is not an INTEGER-PRIMARY-KEY rowid alias

- **Location:** `dist/sqlpipe.cpp:1806`
- **Dimension:** data-integrity
- **Confidence:** high
- **bullseye target:** 🎯T15
- **Invariant violated:** Diff sync (bucket hashes, row hashes, insert/update/delete decisions) assumes a rowid identifies the same logical row on master and replica. This only holds when the PK is an INTEGER PRIMARY KEY (rowid alias). get_tracked_tables (749-770) requires only an explicit PK and rejects only WITHOUT ROWID, so TEXT/composite/non-alias-PK tables are tracked, and for those rowids are assigned independently per database.
- **Failure scenario:** Table `t(id TEXT PRIMARY KEY, v TEXT)`. Master content by rowid {1:'a',2:'b'}; replica has the SAME logical rows but different rowids {5:'a',6:'b'} (arises on any repair path diff sync is meant for: initial sync of two independently-populated DBs, a restore/VACUUM that renumbered rowids, or divergent insert/delete history). Diff by rowid: master rowids {1,2} absent from replica -> insert 'a','b'; replica rowids {5,6} absent from master -> delete_rowids=[5,6]. handle_diff_ready applies the INSERT patchset first: INSERT PK 'a'/'b' hit PK conflicts and are REPLACEd in place (still at replica rowids 5,6), then `DELETE FROM t WHERE rowid=5/6` removes both rows. Replica ends EMPTY while master has {a,b}; the replica transitions to Live and Acks, believing it is in sync, so the divergence is permanent until another converge() is forced. Partial-overlap cases (e.g. master {1:a,3:c,5:e} vs replica {1:a,2:c,3:e}) oscillate — a committed row 'c' is deleted every other round.
- **Evidence:**
  ```

WHERE rowid = ?` (4832) while the INSERT patchset applies by PK — the two identity spaces are conflated

- **Confidence:** high

### F3 — [HIGH] Master discards transmitted bucket_hi and recomputes range span from its own bucket_size, truncating NeedBucketRanges when sides disagree on bucket_size → silent permanent divergence

- **Location:** `dist/sqlpipe.cpp:1699`
- **Dimension:** protocol-correctness
- **Confidence:** high
- **bullseye target:** 🎯T17
- **Invariant violated:** Master and Replica MUST agree on the rowid span of each bucket. Each BucketHashEntry already transmits its own inclusive upper bound (bucket_hi, dist/sqlpipe.h:513); a mismatched bucket range must never leave part of a bucket un-diffed. The wire format carries bucket_hi precisely so the receiver need not assume a bucket_size.
- **Failure scenario:** MasterConfig.bucket_size=1024 (default), ReplicaConfig.bucket_size=4096 (both configurable per-side, header lines 666/746, with NO negotiation or validation anywhere). Table T on master is empty; replica has rows at rowid 1..4000. Replica emits one bucket {table=T, bucket_lo=0, bucket_hi=4095, row_count=4000}. ## Strategic recommendations

## Strategic assessment

**The dominant systemic risk is silent, unrecoverable divergence.** Three of the highest-impact findings — bucket_hi truncation (dist/sqlpipe.cpp:1699), rowid-as-identity in diff sync (:1806), and the auto-flush `flush_pending` leak (:1867) — all share the same terminal signature: the replica ends up holding data the master does not have (or vice versa), reaches the `Live` state, and `Ack`s as though converged. There is no safety net that would catch this. The protocol has no end-to-end post-sync verification (no whole-DB or per-table checksum exchanged after a handshake completes), and the fast-reconnect / queue-replay shortcuts actively *assume* `seq` equality implies data equality (:1521, :4671), so once divergence occurs it is never re-detected on subsequent reconnects. The single most valuable architectural addition would be a cheap, mandatory convergence check at the end of every sync (exchange a full-table rolling hash and `ErrorMsg` on mismatch) plus a periodic background consistency probe. That one mechanism converts every "silent permanent divergence" bug in this report — including ones not yet found — from data-corruption into a detected, recoverable error. This is worth more than fixing each divergence path individually, because the individual fixes are load-bearing and any regression silently re-opens the hole.

**Diff sync rests on an unstated identity invariant that the tracking gate does not enforce.** The whole diff machinery (buckets, row hashes, delete-by-rowid) silently assumes rowid is a stable cross-database row identity, which is only true for `INTEGER PRIMARY KEY` aliases. But `get_tracked_tables` (:749-770) admits any table with an explicit PK and rejects only `WITHOUT ROWID`. The INSERT patchset applies by declared PK (session extension) while deletes apply by rowid — two identity spaces conflated in one transaction. The cheap correct fix is to fail closed: reject non-alias-PK tables at construction, alongside the existing `WITHOUT ROWID` rejection. The "correct but expensive" fix (key everything on the PK) is a larger design change; do the fail-closed guard now and record the PK-keyed diff as a target. Note this invariant is currently documented only as "explicit PRIMARY KEY," which is actively misleading — the docs promise support the engine cannot deliver.

**Exception-safety is not wired in — cleanup is manual and skipped on throw.** `handle_diff_ready` (:4770-4848), `build_insert_patchset` (:1132), and `auto_flush` (:1400) all acquire a resource or global state (open transaction + `foreign_keys=OFF`, an `ATTACH`ed staging DB, the `in_auto_flush` reentrancy flag) and release it only on the straight-line success path. Any throw from the many helpers that *do* throw (`exec`/`prepare`/`step_done`/`write_seq`/`on_flush`) leaks the state, and in two of the three cases (`handle_diff_ready`, `build_insert_patchset`) this poisons the caller-owned `sqlite3*` connection for its entire remaining lifetime — every future `BEGIN` or `ATTACH` fails. Tellingly, the author already got this right in one branch of `handle_diff_ready` (:4798-4804 rolls back and restores FK) and in the sqlift apply path, so the pattern is understood; it just wasn't applied uniformly. The fix is a policy, not a patch: **any function that mutates connection-global state (transactions, PRAGMAs, ATTACH) must use RAII scope guards, no exceptions.** A one-time sweep for `BEGIN`/`ATTACH`/`PRAGMA` without a corresponding guard would find these and likely more. This matters doubly because the connection is caller-owned and long-lived — a leaked transaction is not contained to one operation.

**The deserializer's "throw only sqlpipe::Error" contract is not actually held, and allocation sizing is the leak.** `deserialize` is the primary attack surface (trust boundary at :508), and the codebase clearly *intends* it to reject malformed input with `ProtocolError` (the `check_count`/`kMaxArrayCount`/`kMaxMessageSize` machinery, the fuzz harness that catches only `sqlpipe::Error`, the existing "rejects absurd array count" test). But two attacker-influenced allocation sizes bypass the guards entirely — the LZ4 `original_len` (:371) and `RowHashRun.count` (:610), the latter an `i64` that isn't even in `check_count`'s `uint32_t` domain. Both throw `std::bad_alloc`/`std::length_error`, which escape the contract, abort the fuzzer, and crash in-process callers that guard only `sqlpipe::Error`. The systemic lesson: **every wire-supplied value that sizes an allocation must pass a bounds check before the allocation**, and the type of that value must be in the checker's domain. An audit pass for "wire read immediately feeding `resize`/`reserve`/vector-ctor/`make`" is the right generalization — there may be more than these two.

**The wire format is implemented three times and there is no cross-decoder conformance harness.** Canonical C++ (dist/sqlpipe.cpp), the Go reimplementation (serialize/deserialize/compress.go), and the TS decoder must stay bit-compatible, plus two ad-hoc C-API result encoders. This is confirmed to have already caused two classes of drift: (a) the same allocation bugs are duplicated in Go (compress.go:69, deserialize.go:358) — meaning fixes must land in lockstep or robustness diverges; and (b) the OutMessage/Delivery API migration (commit 31ff645) updated the Go C-API shim but not the Wasm shim, leaving `web/sqlpipe_wapi.cpp` non-compiling and the entire browser boundary dead at HEAD. **CI only runs `cv test`; it never builds `cv wasm`.** Two structural fixes: add the Wasm/emscripten target and the Go cgo build to CI so no binding can silently rot, and stand up a cross-language conformance corpus (a fixed set of messages encoded by each implementation, asserted byte-identical, decoded by each). Without the corpus, the three-way format is a standing source of interop bugs and the "second/third parse of untrusted bytes" trust boundary is unverified.

**FFI robustness is inconsistent with the code's own standards.** `to_buf`'s unchecked `malloc`+`memcpy` (:189, mirrored in wapi:203) will segfault the host process (or silently corrupt Wasm linear memory at offset 0) on OOM, even though sibling functions in the same file check allocation results and return `SQLITE_NOMEM`. And the generic `catch (std::exception)` arms remap everything to `ErrorCode 1 = SqliteError` (:444), so a malformed-message OOM reaches Go callers mislabeled as a database error, defeating any retry-vs-drop routing. Neither is catastrophic alone, but together with the Wasm compile break they show the FFI layer is under-tested relative to the core. Recommend a dedicated FFI error-contract test (fault-inject malloc; assert distinct error codes for protocol vs SQLite vs internal) and a shared `to_buf` that surfaces NOMEM.

**Threading is an assumed-not-enforced invariant.** No locks, atomics, or documented thread-safety contract exist anywhere, yet the header only says objects don't own the `sqlite3*` — it never states the single-thread requirement. The one reentrancy path (commit hook) is the site of the most severe correctness bug (#9). At minimum, document the single-threaded-per-object contract prominently in the public header; the commit-hook flag lifecycle (both `flush_pending` and `in_auto_flush`) should be treated as a small state machine and unit-tested for the commit→transaction→rollback ordering that the current tests miss.

**For the engineer picking this up:** fix in this order — (1) the two `critical`s (#4 rowid identity via fail-closed guard, #9 auto-flush flag reset), because they corrupt data on the happy path with no attacker; (2) the exception-safety cluster (#11, #12, #10) via an RAII sweep, because a leaked transaction wedges a caller's connection; (3) the deserializer allocation bounds (#2, #3) in both C++ and Go together; (4) the Wasm compile break (#6) plus adding wasm+cgo to CI; (5) bucket_hi/bucket_size (#1). Then add the post-sync convergence check as its own target — it is the systemic backstop. Treat #5 (schema fingerprint width) as documentation-only unless a protocol version bump is already on the table.

- The sqlpipe core logic in dist/sqlpipe.cpp (~lines 1-5700) and the public API in dist/sqlpipe.h.

- Transactional/exception safety on the apply paths: `handle_diff_ready` (transaction + `foreign_keys` restoration) and `build_insert_patchset` (`_sqlpipe_stage` ATTACH lifecycle).
- FFI boundaries: the Go C-API shim (go/sqlpipe/sqlpipe_capi.cpp) and Wasm shim (web/sqlpipe_wapi.cpp) — buffer allocation, error-code mapping, and API/ABI consistency with the current OutMessage/Delivery core.
- The Go wire reimplementation (serialize.go / deserialize.go / compress.go) insofar as it mirrors C++ decoder robustness bugs.
- Schema-compatibility gating (`compute_schema_fingerprint`, HelloMsg checks).
- The concurrency model at the level of documented invariants (single-threaded, unsynchronized).

## What this audit did NOT examine (limits of the report)

- **The bundled third-party code was not reviewed:** sqlift (~:5709-8495) and sqldeep/liteparser (~:8496-end). Auto-migration (`auto_migrate_schema`, :790-852) hands remote schema SQL to sqlift with `SQLIFT_ALLOW_ALL` (destructive rebuild) — a significant trust boundary — but the sqlift internals behind that call were not audited.

- **Not covered:** performance/throughput, memory footprint under load, LZ4 correctness beyond the length field, the build system / SQLite compile flags, transport/TLS (out of scope by design — the caller owns transport), authentication/authorization of peers, and version/back-compat of the wire protocol across releases.

## Notes on overlapping findings

Findings are distinct enough that none should be merged, but several share a root cause and should be fixed as clusters (and tested together):

**Cluster A — unbounded allocation from wire-supplied size (single root cause: allocation-driving values not bounds-checked before use, and duplicated across languages).** Collapses:
- "read_changeset trusts wire-supplied decompressed length…" (dist/sqlpipe.cpp:371)

**Cluster C — auto-flush flag lifecycle (tightly coupled pair).** The two commit-hook flag bugs are entangled:

- "auto_flush() leaves the in_auto_flush reentrancy guard set…" (:1400) — currently masked, becomes live only once the first is fixed.
